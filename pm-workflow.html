产品经理 · AI 工作流

用 WorkBuddy 重构产品经理工作流

一个想法在脑子里已经很清楚，但要落成 Demo，却要经历画原型、反复改稿、和研发来回拉扯，最后上线的方案和最初设想早已不同。本文给出一套把「想法」直接翻译成可交互原型与可讨论方案的方法——不用等研发、不用反复画图、也不需要精通代码。

00写在前面

这不是一篇工具介绍，而是一套可复用的工作方法

在接触 AI 之前，产品经理的典型路径是：画原型 → 写文档 → 等排期 → 反复调整。这条链路的问题是，最贵的那部分——思考产品逻辑——反而被最便宜的那部分——画图和对齐——挤占了时间。

重构后的路径变成了：说清楚需求 → 生成可交互原型 → 对照校验 → 直接拿去讨论。产出物从静态线框图升级为能点、能跳、能演示的高保真页面。

本文覆盖产品经理的三个核心工作场景：

  1. 需求迭代的原型设计——在已有产品上改功能
  2. 0-1 的项目原型 + 逻辑验证——从零验证一个想法
  3. 文档的编写与对齐——和研发、业务、老板同步
为什么用 WorkBuddy

它同时具备三件原本要分开做的事：能写代码并跑起来、能托管后端与数据、能直接产出文档和在线分享链接。这意味着原型不再只是本地一个 HTML，而是可以发出去让别人点开看的链接。

01核心认知：WorkBuddy 是「想法翻译器」

重塑认知，是后面所有效率提升的基础

WorkBuddy 的本质是一个高效的翻译器。它无法凭空理解模糊的意图，但只要你能清晰描述逻辑，它就能把想法精准地翻译成可交互、高保真的前端应用。这意味着三件事：

  • 解放双手：从繁琐的画图工作中解放，告别像素级对齐和组件拖拽。
  • 聚焦思考：精力投入到梳理产品逻辑、定义用户流程、构思交互细节上。
  • 高保真交付：原型不再是静态线框图，而是动态的、可交互的页面，还能一键发布成链接。
一句话原则

你的逻辑表达越清晰，还原度越高。与其花时间学提示词模板，不如花时间把业务逻辑想清楚。

02协作原则：小步快跑，增量迭代

最重要的一条原则，没有之一

与其试图用一段冗长而复杂的指令生成完美系统，不如把目标拆解成一个个具体、明确的小步骤，通过持续的、增量式的迭代逐步完善。这套方法论就是「框架—组件—交互—校验」四步走：

搭框架生成最基础的页面布局和结构
填组件逐步加入按钮、输入框、列表
调交互注入点击、跳转、数据加载
校验沉淀对照还原 + 沉淀规范文档

始终记住：每一次交互只关注一个具体、明确的目标。这样不仅能保证理解准确率，也让你始终掌控项目进展和方向。

反例

「帮我做一个电商 Agent，要能搜索商品、下单、售后，前端要好看，后端用 ReAct」——这种一次性大需求，是返工率最高的用法。

03一次性环境准备

做完这步，后面所有场景都顺滑

3.1 接入 MCP（可选但强烈建议）

MCP 让 WorkBuddy 能主动打开网页自查、读取设计稿。配置文件路径是 ~/.workbuddy/mcp.json（注意是 mcp.json，不是 .mcp.json）。

{
  "mcpServers": {
    "Playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest", "--extension"]
    },
    "Figma AI Bridge": {
      "command": "npx",
      "args": ["-y", "figma-developer-mcp", "--stdio"],
      "env": { "FIGMA_API_KEY": "替换为你的 key" }
    }
  }
}
别忘了这一步

保存配置后，需要到连接器管理页面对新添加的服务点击「信任」，否则不会生效。Figma Key 获取路径：登录 Figma 网页版 → 头像 → Settings → Personal access tokens → Generate new token。

3.2 浏览器自动化

用于让 AI 打开自己刚写的页面做视觉校验、对照参考网站、模拟用户走流程。若浏览器控制未开启，可在设置 → Agent → 浏览器控制中开启；未开启时也可用内置的浏览器技能完成同类操作。

3.3 占位资源约定

  • 图标：在需求里指定图标库，例如「图标统一用 react-icons」或「用 Ant Design 的 Icon 组件」，避免 AI 自绘或留空白。
  • 图片：可以指定从 Unsplash 取图并要求逐条验证链接可访问；更省事的做法是直接让 WorkBuddy 生成配图，省掉找图和验链的环节。

04场景一：需求迭代与原型设计

在已有产品上加功能，从 2 人天到 0.5 人天

过去（Old School）
  • 在 Axure/Figma 里反复拖拽，为一个按钮对齐纠结半天
  • 产出低保真线框图，与最终效果差异巨大
  • 拿着线框图向老板、UI、研发解释「这里以后是彩色的」
  • 沟通成本高，信息损耗严重
时间成本：2 人天起步
现在（WorkBuddy Flow）
  • 一张截图或一个设计稿链接直接喂进去，生成高保真页面
  • 任何调整直接用自然语言描述，当场修改即时生效
  • 可发布成在线链接，老板和研发自己点开看
  • 会上决策、会上改完、会后发链接
时间成本：约 0.5 人天

配置建议：智能体模式 + Playwright MCP（可选 Figma AI Bridge）。以下以「给某个 Profile 页面右侧增加侧边 Agent 聊天面板」为例。

1

还原现状：让 WorkBuddy 看懂你的产品

要在现有产品上做迭代，首先得让它看懂当前页面。两种方式：

方式 A · 页面截图法（最直接）把要迭代的页面完整截图，连同提示词一起发过去。

提示词 · 截图还原根据我给你的这张设计图，帮我 1:1 还原一个前端 HTML 页面。这只是一个用于需求沟通的 Demo，不需要连接后端接口，页面数据全部前端写死。技术栈使用 React。

方式 B · 设计稿法（有 Figma 时更高效）粘贴 Figma 素材地址，让 AI 读取设计稿还原。

提示词 · 设计稿还原请使用 figma ai bridge mcp，读取我的设计图 https://... 帮我 1:1 还原一个前端 HTML 页面。不需要接入后端，因为我的项目是一个仅前端用于需求同步的 Demo，页面数据都采取前端写入的方式。语言使用 React。
提示词心得

核心是告诉它你的目的和约束。不需要长篇大论，但必须包含：这是 Demo 不用接后端、用什么技术栈、数据怎么来。

2

还原效果检查

初次实现多少会和参考页面有差异，这一步用浏览器能力让 AI 打开自己写的页面，把代码和最终呈现对上号。进阶用法：让它同时打开你的参考网站，对照参考站的样式实现，检查自己哪些地方没做到还原。

提示词 · 对照校验请用 playwright mcp 打开你目前实现的前端页面，以及我给你的参考网站 https://...。我希望你对照两者的前端样式，检查还有哪些模块没有做到 1:1 还原（前面给你的设计图就来源于这个参考网站）。 检查时请特别关注以下维度： - 字号大小的层级关系 - 容器之间的间距与对齐 - 颜色系统
3

细节微调：搞定「倔强」的 AI

总有些细节反复修改依然错漏。这通常意味着它惯用的解决路径遇到了障碍，需要我们提供更精准的导航。

用 classname 精准定位：打开浏览器检查（右键 → 检查，或 F12），用元素选择器定位目标元素，在 DOM 树中双击复制 classname。

提示词 · 精准定位目前我观察到前端的 {{classname}} 还没有按我的要求还原。图 1 是我现在的实际效果（粘贴截图），我希望你按图 2 的样式做还原（粘贴期望截图）。 你也可以用 playwright mcp 打开参考网站 https://... 查看 {{参考网站对应组件 classname}} 的实现，并在我的项目中 1:1 还原它。
4

需求落地：让原型「动」起来

做迭代基本没有设计图参考，考验的是用文本表达交互的能力。方法论是用「用户视角」描述，说清楚五件事：从什么位置起始 → 通过什么操作 → 点击后发生什么 → 在哪个位置出现 → 出现什么内容。

务必带上规范文档

提需求时记得携带 FRONTEND_SPEC.md（见第七节），否则新增模块会和已有风格打架。

提示词 · 新增交互模块现在我希望在页面右侧区域增加一个聊天窗口。 1. 这个聊天窗口由顶部导航栏右侧、claim anniversary 容器左侧的 chat 图标激活。 2. 激活聊天面板后，右侧 main 内容容器往左自适应挤过去。 3. 聊天面板由三部分组成：顶部是标题；中间是消息展示区，分为用户与 agent 的消息，不需要头像；下方是输入框与发送按钮。 实现时需要符合我的 FRONTEND_SPEC.md 规范。

基础交互完成后想加打字机效果、知识库查询等，沿用同一套方法：从用户操作视角出发，说清起始、操作、反馈、位置、内容。

场景一关键总结

要点说明
提示词三问需求表达清楚了吗？定位问题的参考信息给足了吗？目标实现的参考信息给足了吗？给出手段可以是文本、截图，也可以是让它自己打开参考站去看。
启动脚本让 AI 写一个 sh 启动脚本，固定端口、端口被占用时先清理、启动后在终端打印访问地址。
规范文档让 AI 总结一份前端规范 md，后续迭代在需求前面带上它，保证风格统一。

05场景二：0-1 项目原型与逻辑验证

如果需求迭代是「术」，0-1 验证更考验「道」

过去（Old School）
  • 对着一堆接口文档干瞪眼，看着字段猜后端逻辑
  • 验证路径极短，中间过程完全是黑盒
  • 遇到复杂算法、Agent 交互不知其所以然
  • 与研发讨论时提不出建设性意见，无法把控风险
现在（WorkBuddy Flow）
  • 通过自然语言描述把完整逻辑跑通，结合输出的流程图看懂业务流转
  • 不再只是需求提出者，可以直接交付逻辑合理、甚至代码可用的方案
  • 需要真实后端时，可用云数据库、文件存储、用户认证与免密钥大模型调用直接托管
  • 验证完还能发布成链接，让业务方自己上手体验

配置建议：智能体模式 + Playwright MCP。以下以「电商场景 Agent，帮 C 端用户搜索商品并指定商品」为例。核心思路与场景一完全一致：小步快跑，增量迭代。

1

搭建基础聊天页面

提示词 · 0-1 启动我的项目是一个对话式电商 agent，移动端尺寸。请以移动端 iPhone 12 的尺寸，帮我创建一个基础的 agent 聊天页面，前端使用 React。 页面结构：顶部是对话标题；中间是 agent 与用户的消息记录，不需要头像；底部是输入框与发送按钮。 现在请帮我实现这个项目的基础页面结构。

为了后续迭代方便，顺手补充两个优化点：

提示词 · 两项优化1. 请将前端页面的 classname 做规范化处理，方便我以后直接通过 classname 找到对应代码，而不是用 React 生成的 classname。 2. 请帮我创建一个 sh 启动脚本，固定端口启动；当目标端口被占用时，先清理占用进程再启动；启动成功后在终端打印项目访问路径。
2

接入基础对话能力：文档先行

这一步开始涉及后端逻辑。如果对技术实现不熟，没关系——先让它当你的技术顾问，写一份实现文档，并且在你确认之前不许动任何代码。

提示词 · 文档先行我现在打算在项目里实现真正的 AI 对话。我希望实现后：用户在输入框输入文本、点击发送后，模型思考后回复，能看到折叠的 thinking 与最终回复文案，thinking 默认折叠、可展开但限制在一定高度内查看。 同时，用户发送第二条消息后，AI 能理解上下文并基于上下文继续回复。 请你根据以上需求帮我写一份实现的 md 文档，并且在得到我开始研发代码的确认消息前，不要修改我的任何代码文件。

先让它写实现文档，后续实现会更准确。方案不确定的地方，可以在反复交互中逐步完善文档。代码写完后，同样让它用 Playwright 打开项目、模拟用户走完整个流程。

3

实现核心业务逻辑：商品搜索

思路相同：自己不清楚怎么实现，就先让它出实现文档；已经想清楚了，就直接提需求。

提示词 · 核心业务请为这个 agent 实现对话过程中的商品搜索能力。 首先创建一个本地数据库存储商品信息，至少包含商品 id、主图、标题、价格、详情描述。 在用户与 agent 的交互中，识别用户意图是否涉及商品搜索；若涉及，调用商品搜索 MCP（基于上面创建的数据库实现），把用户提问转换成商品标题关键词并搜索。 拿到商品信息后，agent 返回可交互的商品卡片消息气泡，支持分页，一页 4 个，最多 5 页共 20 个。卡片呈现主图、标题、价格，右上角有一个文本「追问」按钮。 用户点击追问后，输入框上方呈现「正在追问哪个商品」的交互；追问状态下发送消息时，用户消息气泡中携带被追问商品的 tag。 还需要一个应对追问的 MCP：识别到追问后，根据商品 id 查询详情描述，并据此给用户文本描述。 为了方便模拟，所有商品标题都携带「风衣」关键词。完成代码后，请使用 playwright mcp 模拟用户搜索风衣、并针对某个风衣追问的场景，完成一轮商品搜索与追问的交互与逻辑测试。

即便指令再详尽，初版实现也可能有问题。没关系，继续通过追问修正：

提示词 · 追问修正我发现了几个问题，请帮我修改： 1. 页面尺寸需要严格按移动端尺寸，不能因为消息气泡内容长短撑开整个页面。 2. 触发调用工具时，需要有一般 agent 产品那样「正在调用 xx 工具」的交互。 3. 后端实现思路应基于 ReAct：用户一条消息可能触发多次 AI 请求，第一次判断需要调用工具，第二次结合工具结果回复。 4. 既然后端是多轮思考，前端配套交互也要做对应调整与优化。
这一步的价值

你像架构师一样思考，把复杂业务流程拆解成清晰的模块，而 AI 把思考变成现实。最终得到一个前后端完整的 MVP，后续可以基于它做逻辑验证和复杂逻辑迭代。

06场景三：文档的编写与对齐

产品经理不仅要创造，更要频繁同步与对齐

过去（Old School）
  • 收集资料容易，整理成逻辑清晰的文档难
  • 在 PPT 里画框架图、流程图，反复调整仍觉得逻辑不通
  • 大量时间浪费在调格式、对齐图形上
时间成本：1 人天
现在（WorkBuddy Flow）
  • 想到什么写什么，把参考资料一股脑丢进文档，逻辑混乱也无所谓
  • 把这堆原料交给 AI，结合明确的整理方法论瞬间完成结构化与可视化
  • 还能直接产出 Word、PPT、表格，或沉淀进资料库分享
时间成本：约 0.5 人天

6.1 项目文档与研发对齐

先把草稿暴力写下来，逻辑混乱完全没关系：

我想要跟研发团队同步，以及业务团队同步我的这个电商的 agent 是用来干什么的。它其实是给 C 端用户用的，能够让用户在对话的情况下完成下单。目前支持的场景就是搜索商品，以后可能还会支持下单、做售后等场景。所以后面除了对接商品库，还要对接售后的接口。这个 agent 会自己意图识别用户想干什么，再去调用不同的工具来帮用户解决问题……

然后让它按你的原则整理成专业文档：

提示词 · 草稿结构化请根据我下方给的草稿，以及当前项目的实现，帮我写一份方便跟其他同事同步的 md 文档。 整体以总分结构编写：先通过总结让读者读懂文档要表达什么，再分别展开每个模块。尽可能简单表达，让小白一眼看懂。 关于 AI 的实现方面，需要输出一个 mermaid 框架图与时序图，方便我与开发同步实现逻辑，以及未来可能需要对接的数据库或 API 能力范围。 以下是我的文档草稿： {{粘贴你的意识流草稿}}

6.2 竞品分析与市场洞察

同一套「随性打草稿」的方法，做调研时同样好用：

  1. 暴力粘贴：看到有效的信息、文章片段、数据，一股脑贴进一个文档。
  2. AI 整理：把这堆杂乱信息交给 AI，让它结构化并提取核心观点。
  3. 可视化输出：让它输出 mermaid 框架图，或直接生成一张配图放进文档。

这套工作流能确保精力都花在「收集高价值信息」这个核心环节上，把整理和排版的脏活外包出去。

额外优势

文档产出后可以直接转成 Word 或 PPT 交付，也可以沉淀进资料库跨设备访问与分享——这部分是传统 AI IDE 不具备的。

07项目规范沉淀

项目达到基础可用状态后，务必做这两件事

7.1 编写启动脚本

让 AI 写一个 sh 启动脚本，之后每次启动项目只需在终端执行它。建议加上两个细节：固定端口（允许清空占用再启动，防止端口冲突）、打印地址（启动成功后打印访问地址）。

提示词 · 启动脚本请帮我创建一个 sh 的 start 脚本，方便我每次启动项目只需要在终端执行它。我希望脚本每次都固定端口启动，遇到端口被占用时先清理占用进程再启动，保证每次都能用固定端口。启动成功后，需要在终端打印出访问地址。

7.2 沉淀前端规范文档 FRONTEND_SPEC.md

让 AI 总结一份前端规范 md。后续继续迭代时，在需求前面带上这份文档让它遵守，能保证样式风格统一、布局更合理。建议至少包含：项目前端页面的基础布局、字号大小系统、颜色系统、间距系统。

提示词 · 规范文档请根据当前的样式实现，帮我创建一份前端规范的 md 文档。这份文档后面将作为我的项目设计规范使用。规范里至少需要包含以下模块： - 项目前端页面的基础布局 - 字号大小系统 - 颜色系统 - 间距系统

7.3 实现文档先行

对实现方案不确定的地方，都先让它写实现文档，确认后再写代码。这是避免大规模返工最有效的一招。

08微调四板斧

当 AI 反复改不好、甚至「嘴硬说改好了」时的处理顺序

手段怎么做适用场景
细致表达 运用 classname、截图、浏览器打开页面等方式，把没实现的地方更细致地表达出来；或详细用自然语言描述现状 vs 期望，让它根据现状代码猜测原因 定位不到问题所在时，首选
指定维度 如果你大概知道问题维度（flex 布局、z-index 层级等），直接让它往这个维度思考 你有技术直觉时，最快
重置上下文 新开一个会话，避免上下文过长导致模型产生临时「思维定式」 越改越乱、反复打转时
更换模型 WorkBuddy 的模型由当前会话决定，无法为单个任务临时切换。替代做法是换一个会话环境再试，或结合上面三招 能力受限 需变通
与原方法的差异

原方案把「换模型」当作终极手段之一（如切到 GPT-5.2 / GPT-5.1，利用不同模型的习惯性解法覆盖问题）。在 WorkBuddy 中这一招退化为「新开会话 + 指定维度 + 更细致表达」，实践中基本够用，但确实少了一个可调变量，需要在描述精度上补回来。

09提示词速查

自由随性即可，重点是把这三件事说清楚

场景关键要素
页面还原参考物（截图 / 设计稿 URL）+ 约束（只是 Demo、不接后端）+ 技术栈
对照校验打开自己实现的页面 + 打开参考网站 + 明确检查维度（字号层级 / 间距对齐 / 颜色系统）
细节微调classname 定位 + 现状截图 + 期望截图，或直接指明参考站的对应组件
新增交互起始位置 → 操作 → 反馈 → 出现位置 → 出现内容；并带上 FRONTEND_SPEC.md
0-1 启动项目定位 + 端型尺寸 + 技术选型 + 页面结构划分
文档先行完整描述期望效果，并明确「确认前不要修改任何代码文件」
逻辑测试指定测试场景 + 指定用 Playwright 模拟用户走完整流程
文档整理意识流草稿 + 结构要求（总分 / 小白能懂）+ 图表要求（mermaid 框架图、时序图）
通用三问

每次发提示词前过一遍：需求表达清楚了吗？定位问题的参考信息给足了吗？目标实现的参考信息给足了吗？表达手段可以是文字、截图，也可以是让它自己打开网页去看。

10与原方案（AI IDE 方案）的差异

方法论可以原样迁移，工具特性有两处不同

环节WorkBuddy 上的情况替代度
截图 / 描述还原高保真页面直接生成项目文件并本地实时预览完整替代
Figma 设计稿还原支持接入 MCP，需手动配置并信任一次性配置
浏览器自检 / 对照参考站 / 模拟用户内置浏览器自动化，也可挂载 Playwright MCP完整替代
classname 精准定位微调同样按 classname 定位并修改代码完整替代
更换模型绕开思维定式模型由会话固定，不能按任务切换部分替代
重置上下文新开会话即可完整替代
本地数据库 + 工具调用 + 后端逻辑可写代码跑服务，也可用云数据库、文件存储、用户认证、免密钥大模型调用托管后端替代且更强
md 文档 + mermaid 图产出 md，并能直出 Word、PPT、表格，可沉淀进资料库替代且更强
原型交付给老板 / 研发可一键发布为在线分享链接增量能力
占位配图可直接生成配图，省去取图与链接校验增量能力

交互形态的不同

AI IDE 是「智能体 + 文件树 + 终端」的 IDE 心智，习惯盯着 diff 逐行确认；WorkBuddy 是通用智能体的对话式推进，靠对话和工具调用完成。对非技术背景的产品经理反而更友好，但如果你习惯了逐文件审阅，需要一点适应期。

11落地清单

照着做一遍，这套工作流就是你的了

一次性准备

  • 把 Playwright、Figma AI Bridge 写入 ~/.workbuddy/mcp.json，并在连接器管理页点击「信任」
  • 确认浏览器自动化可用（设置 → Agent → 浏览器控制）
  • 约定好图标库与配图来源，写进常用提示词前缀

每个项目固定三件事

  • 先产出 FRONTEND_SPEC.md：间距 / 颜色 / 字号层级 / 布局框架，之后每次需求前置携带
  • 生成固定端口启动脚本，或直接使用内置预览
  • 复杂逻辑先出实现文档，确认后再写代码

每次提需求的三问

  • 需求表达清楚了吗？
  • 定位问题的参考信息给足了吗（截图、classname、参考站 URL）？
  • 目标实现的参考信息给足了吗？
最后

这套方法让我们真正拥有了把想法直接落地的能力，把更多时间花在思考产品逻辑和用户体验上，而不是纠结于具体的代码实现。工具会变，但「小步快跑、文档先行、规范沉淀」这套方法不会变。
